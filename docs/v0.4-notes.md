# v0.4 — Service Budget, Shuffle Sharding, 장애, Aging, 결과 저장

v0.4 는 아키텍처 구성 요소를 완성하는 반복이다. 포괄적 실험·통계·결론은 v1.0 으로 미룬다.

## 실행

```bash
export JAVA_HOME=/Users/ariel/Library/Java/JavaVirtualMachines/openjdk-21.0.2/Contents/Home
./gradlew run --args="--suite=v04 --quick=true"            # 스모크: warm-up 0, 측정 1, 축소 워크로드
./gradlew run --args="--suite=v04"                         # 전체 크기 (warm-up 1, 측정 3)
./gradlew run --args="--suite=v04 --output-dir=out --base-quantum=10"
```

결과는 `<output-dir>/v04[-quick]-<UTC 시각>[-n]/` 에 저장되며 기존 디렉터리를 덮어쓰지 않는다.
`--suite=all` 에는 v04 가 포함되지 않는다 (v0.3 suite 보존).

## 실험 arm

| ID | 구성 |
|---|---|
| E0 | FIFO |
| E1 | DWRR |
| E2 | WDEDF (업무 목표, Λ=5%) |
| E3 | E2 + 서비스 클래스별 큐 + Service Budget |
| E4 | E3 + Shuffle Sharding (기본 4 샤드, 부분집합 2, seed 42) |
| E5 | E4 + Aging (기본 threshold 30 s) |
| E4-F, E5-F | E4/E5 + 샤드 1 장애 [10 s, 40 s) (F1 시나리오) |

## 설정 (`ServiceBudgetConfig`, `ShardingConfig`, aging threshold)

| 설정 | 의미 | 종류 |
|---|---|---|
| `otpWeight : advertisementWeight` (기본 3 : 7) | 두 클래스 모두 선택 가능한 작업이 있을 때 dispatch 슬롯 비율 (smooth weighted round robin) | **예약** — 한 클래스에 작업이 없으면 다른 클래스가 그 몫을 쓴다 |
| `otpLimitBasisPoints`, `advertisementLimitBasisPoints` (기본 0 = 없음) | 클래스 dispatch 율 상한 (provider 용량 대비, 메시지 단위 토큰 버킷) | **하드 리밋** — 빌려 줄 수 없음 |
| `tenantRateBasisPoints`, `tenantBurst` (기본 80%, 50) | 테넌트 전역 dispatch 율 상한 (cost 단위 토큰 버킷) | **하드 리밋** — 테넌트의 모든 클래스 큐·샤드가 하나의 버킷을 공유 |
| `shards`, `subsetSize`, `seed` | 샤드 수, 테넌트당 배정 샤드 수, 결정론적 배정 seed | 샤드 용량 = provider 용량 / shards |
| `failures` | `(시각, 샤드, 장애/복구)` 목록. 장애 샤드는 반드시 복구되어야 한다 | |
| aging threshold | `순서 키 = min(업무 목표, 도착 + threshold)` | |

기본값은 근거 있는 최적값이 아니라 실험 선택값이다.

## 동작 요약

* **엔진**: `SchedulingPolicy.nextEligibleTime(now)` 추가 (기본: 대기가 있으면 `now`). `now` 가 아니면
  엔진은 그 미래 시각에만 dispatch 판단을 다시 예약한다 (`MAX` 이면 도착·복구 사건을 기다림). 더 이른
  판단이 필요해지면 새 사건이 이전 사건을 대체한다. 같은 시각 재예약 없음. 기능을 끄면 v0.3 과 사건
  순서가 동일하다 (골든 테스트).
* **예산 게이트**: WDEDF 는 메시지를 꺼내거나 deficit 을 쓰기 전에 게이트를 확인한다. 막힌 ACTIVE 큐는
  메시지를 꺼내지 않고 heap 에서 주차 목록으로 옮겼다가 재개 시각에 되돌린다. 게이트를 통과하는 큐가 없으면
  라운드를 넘기지 않는다 (시간이 멈춘 채 quantum 이 쌓이지 않음). 차입도 게이트를 확인한다.
* **서비스 클래스 큐**: 테넌트×유형 큐 키 (`A/OTP`) 를 재사용하되 클래스별 WDEDF 로 분할하고, 테넌트 가중치를
  자식에게 나누지 않는다 (v0.3 S5 의 몫 누출 방지).
* **Shuffle Sharding**: 도착 시 배정 부분집합의 정상 샤드 중 대기가 가장 적은 샤드로 라우팅한다. 샤드는
  독립 용량을 갖고, 전역 provider 한도도 계속 적용된다. 장애 샤드는 새 dispatch·라우팅에서 빠지고 대기
  메시지는 복구까지 보존된다.
* **Aging**: 순서 키만 바꾸며 deadline 은 그대로이다. 키가 enqueue 시 고정되므로 heap 순서가 항상 올바르다.

## 불변식 (실행기가 매 실행 검증, 위반 시 예외)

메시지 보존 · provider 용량 위반 0 · 독립 감사로 본 테넌트 예산 위반 0 · 샤드 용량 위반 0 · 반복 실행 결과
동일.

## 영향 범위 (blast radius) 정의

같은 arm·같은 워크로드에서 장애 유무를 비교한다. aggressor 가 아닌 테넌트는 다음 중 하나이면 "영향받음":
deadline miss 율 증가 > 1 %p (분모: 그 테넌트의 수신 수), 또는 E2E p99 > 기준 × 1.5 이면서 1 s 이상 증가.

## 출력 파일

`manifest.json`, `experiment-config.json`, `experiment-results.json`, `experiment-summary.csv`,
`tenant-metrics.csv`, `message-type-metrics.csv`, `scheduler-metrics.csv` (긴 형식: 진단값과
`shard.N.utilization`). 가상 시간은 정수 μs, 실행 시간은 정수 ns, 빈 값은 CSV 빈 칸 / JSON `null`.
직렬화는 모든 실행이 끝난 뒤 수행되어 시간 측정에 포함되지 않는다.

## 알려진 한계

* 샤딩은 작업 보존적이지 않다: 테넌트는 배정 샤드 용량만 쓸 수 있다 (4 샤드·부분집합 2 → 최대 50%).
* 장애 샤드의 대기 메시지는 다른 샤드로 옮기지 않는다 (복구까지 대기).
* 장애는 샤드 arm (E4/E5) 에만 적용된다. E0–E3 에 대응하는 "worker 일부 장애" 모델은 없다.
* 클래스 리밋은 메시지 단위이다 (cost 단위 아님). 예산은 MESSAGE_RATE 시나리오만 검증했다.
* 샤드 용량 위반은 샤드 풀 자체 계수이다 (provider 감사처럼 완전히 독립된 감사는 아님).
* 클래스 예약은 테넌트 가중치보다 우선한다: 스모크 S12 에서 E3 (3:7) 은 광고 테넌트에 70% 를 보장해
  OTP miss 율이 E2 보다 높았다 (98.2% vs 78.0%). 이는 설정의 결과이며 v1.0 에서 평가해야 한다.
* 스모크 결과는 quick 모드 (1 회 측정, 축소 워크로드) 이며 결론의 근거가 아니다.
